# 모드 카탈로그 조회 및 100건 초과 처리 검토

기준일: 2026-11-21  
범위: **조회 방식 및 자동 테스트 검토**. 기존 홈/모드/서버 화면 UI는 사용자 요청에 따라 변경하지 않는다.

## 현행 코드와 보안 경계

- `app/(private)/mods/page.tsx`는 `getOwnerAccess()` 성공 시에만 조회하며, `owner_id`를 현재 로그인한 사용자로 제한한다. Supabase RLS는 별도 계층에서 적용된다.
- 이름/Workshop ID 검색, 사용·보관·전체, B42.22/멀티 상태, 최근·오래된·이름순 정렬을 지원한다.
- `limit(100)` 이후 조회 결과가 100건이면 경고만 보여준다. **101건 이후로 이동하는 방법은 아직 없다.** 데이터가 DB에서 사라지는 것이 아니라 현재 화면 조회 범위에서 빠지는 것이다.
- `/mods/[id]`는 UUID 형식 확인, 소유자 확인 후 상세·실제 Mod ID·조사 출처를 읽는다. 잘못된 조사 페이로드는 표시하지 않으며, 모드 ID와 Workshop ID를 혼동하지 않는다.
- 시험 DB 카탈로그는 현재 0건이므로 100건 초과의 실제 UI 동작은 검증되지 않았다.

## 이번에 보강한 회귀 테스트

`lib/catalog-read.ts`는 화면을 바꾸지 않고 기존 조회 조건 정규화/적용 및 상세 조사기록 정리를 분리한 순수 함수다.

`tests/catalog-read.test.ts`에서 검증하는 계약:

1. 기본 최근순·활성 모드 필터 및 허용하지 않는 URL 조건의 제거
2. 숫자 Workshop ID 정확 일치와 일반 이름 검색의 구분
3. LIKE 검색 특수문자(`%`, `_`, `\\`) 이스케이프
4. 보관/전체와 날짜/이름 정렬 조합
5. 검색어 길이 80자 제한
6. 상세 경로 UUID 유효성 검사
7. 유효한 조사 기록 유지, 잘못된 페이로드 제외, 복수 Mod ID·미확인 상태 유지
8. 현재 100건 상한의 명시적 검사 (**101건 이상 지원 검증이 아님**)

이 테스트는 DB에 가상 모드를 INSERT하지 않는다. 소유자 범위 제한은 호출부에서 유지되므로 정적 검사만으로 실제 RLS 동작을 증명하지 않는다.

## 100건 초과 처리 권장안 — 구현 보류

기본적인 사용자 경험은 후속 모드 화면 UI 결정 시 확정한다.

- **1차 구현 제안:** URL 쿼리 `page`로 서버 페이지 이동. 한 페이지 50~100건을 조회하고 필터/검색/정렬을 유지한다. 결과보다 하나 많은 행을 조회해 다음 페이지 존재 여부를 판단하면 전체 `COUNT(*)` 실행을 줄일 수 있다.
- **정렬 안정성:** `created_at`, `title` 값이 같을 수 있으므로 `id` 또는 고유 `workshop_id`를 마지막 정렬 기준으로 사용해 페이지가 겹치거나 누락되는 위험을 줄인다.
- **권한:** 모든 페이지에서 `getOwnerAccess()`, `owner_id` 범위, RLS를 유지한다. 페이지 번호·크기는 서버에서 검증하고 임의의 무제한 조회를 허용하지 않는다.
- **규모 증가 시:** 수천 건 이상에서는 오프셋보다 커서(keyset) 페이지네이션이 더 적합할 수 있다. 다만 현재 계획된 모드 수 규모에서는 간단한 페이지 방식이 우선이다.
- **후속 필수 검증:** 가상 130건에서 페이지 경계/중복/누락, 필터 변경 후 페이지 초기화, 동일 타임스탬프/이름의 정렬, 모바일 조작 및 2개 이상 사용자 격리.

**현재 결정:** 이번 브랜치에서는 실제 페이지 이동과 화면을 추가하지 않는다. 사용자 요청대로 모드 UI 디자인은 이후에 확정한다.

## 변경 금지/미검증

- 운영 배포, `main` 병합, DB 데이터·권한·정책 변경 없음.
- 시험 환경에 101개 실데이터를 삽입하지 않음.
- 사용자 최종 승인 전 카탈로그 자동 등록 없음.
