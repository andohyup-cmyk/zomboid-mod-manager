# 모드 정보 수정·보관·복원 사전 설계 (미승인 DB 변경 없음)

상태: **안전한 요청 검증 로직과 테스트만 준비**. 2026-11-21 시험 DB 현황 기준.  
기본 원칙: 기존 홈·모드·서버 화면 디자인 및 데이터 변경 없이, 현재 승인된 개인 계정 보안 경계 유지.

## 1. 실제 시험 DB 확인 사항

시험 Supabase `smofdbjgcgdmscamknpw`의 `public.mods`:

- 컬럼 `title`, `description`, `is_archived`, `updated_at` 존재.
- `authenticated`는 테이블 SELECT 가능, **UPDATE/DELETE 권한 없음**.
- RLS `SELECT`, `INSERT` 정책만 있고 **UPDATE 정책 없음**. 현 상태에서 카탈로그 수정을 허용해서는 안 된다.
- `updated_at`의 기본값은 `now()`이지만 **업데이트 자동 갱신 트리거가 없음**. 수정 API를 열기 전 새 시점을 원자적으로 기록하는 방안이 필요하다.
- `profile_mods.mod_id`와 `mod_ids.mod_id` 등은 `mods.id`를 외래 키로 참조하며 삭제 시 연쇄 삭제될 수 있으므로, **삭제 대신 보관 플래그만 변경**한다.
- 실제 카탈로그 등록 모드 0건. 3단계에서 모의 레코드로 DB UPDATE를 실행하지 않았다.

## 2. 현재 안전하게 준비한 로직

`lib/catalog-mutation-preview.ts` — 순수함수 `planCatalogMutation(input, snapshot)`:

1. 서버가 미리 조회한 현재 레코드 `snapshot`과 **명시적 요청**을 대조한다. 브라우저가 제공한 snapshot은 신뢰하면 안 된다.
2. `edit_metadata`: 제목(1~200자)과 설명(최대 4000자) 변경만 계획한다.
3. `archive` / `restore`: 오직 `is_archived=true/false`만 계획한다. 서버 프로필 선택·순서, 게임 Mod ID, 조사 원본에는 변경 없음.
4. 사용자가 읽어 본 `updated_at`이 현재 레코드의 시점과 다르면 `stale`을 반환한다. 날짜 문자열을 임의로 정규화하면 마이크로초 정밀도의 DB 값을 망가뜨릴 수 있어 **정확히 일치**시키도록 준비.
5. 잘못된 UUID, 빈/중복 수정, 필드 형식 오류, 과도한 길이, NUL, 허용되지 않은 필드를 거부한다.
6. `workshop_id`, `owner_id`, 실제 게임 `mod_ids`, 조사 출처, B42.22/멀티 확인 상태를 임의 변경할 수 없다. 호환성 확인값 변경은 근거/확인일 저장 경로 확정 후 별도 구현한다.
7. **현재 API·UI에서 이 로직을 호출하지 않는다. 실행 가능한 DB 쓰기 경로가 추가된 것이 아니다.**

## 3. 실제 수정 기능 적용 시 별도 승인 필요한 절차

1. 코드·실데이터 백업 확인. 환경 이름/프로젝트 ID가 **시험 Supabase**인지 재확인.
2. RLS `UPDATE`의 `USING`·`WITH CHECK`에 소유자 `auth.uid()`와 `is_authorized_user()` 모두 적용. `authenticated` 대상 테이블 UPDATE 최소 권한 범위를 검토. **권한 변경은 사용자 승인 전 금지**.
3. 서버 전용 API가 `getOwnerAccess()`, same-origin, 허용된 배포·Supabase 프로젝트, 소유자 UUID를 점검한 뒤에만 변경하도록 구현한다. 서비스 롤 키나 SECURITY DEFINER 우회 금지.
4. UPDATE는 **현재 `updated_at`과 비교하는 조건부 쓰기**로 수행하고, 새 `updated_at`은 DB에서 같은 트랜잭션에 갱신한다. 경쟁 요청으로 변경 행이 0건이면 409 충돌을 반환하고 재조회하도록 안내한다.
5. 수정 이력과 복원 경로의 보존 여부를 확인한다. 승인 후 변경된 내용이 원본 조사 기록을 덮어쓰지 않게 한다.
6. 허용된 계정/미허용 계정/익명, 빈 값, 잘못된 변경, 동시 요청, 보관 후 프로필 활성/순서 유지, 재활성화/복원을 시험 DB에서 실검증한다.
7. **운영 환경 적용과 `main` 병합은 그 뒤에도 별도 승인**을 받는다.

## 4. UI 및 확정 요구사항

- **모드/홈/서버 UI는 사용자가 나중에 조건을 제시하기 전까지 개편하지 않는다.**
- 카탈로그 제목·설명 수정과 보관/복원은 사용자 명시적 조작이 있을 때만 한다.
- 보관은 삭제가 아니며 기존 프로필의 모드 연결과 로드 순서 원본을 유지한다.
- Workshop ID는 Steam 항목 식별자, `mod_ids.value`는 게임 Mod ID이므로 혼동하지 않는다.
- 정보의 출처/확인 시점과 B42.22·멀티 호환성은 근거 없이 `confirmed`로 바꾸지 않는다.

## 5. 현재 미검증/중단선

- 브라우저에서 실제 수정·보관·복원 버튼 클릭: 미구현.
- 실제 DB UPDATE/권한 변경: 미실행·미승인.
- `updated_at` CAS의 실제 PostgREST/RLS 동시성 테스트: 미실행.
- 새로운 UI와 호환성 증거 편집 워크플로: 사용자 추후 결정.

**이 문서는 승인 요청이 아닌 구현 준비 자료다.**
